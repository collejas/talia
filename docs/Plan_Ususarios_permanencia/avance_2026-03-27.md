## Hallazgos de baseline (MCP Supabase + código)

1. Se observó patrón de relogin recurrente cercano a 60-65 minutos en `auth.audit_log_entries`.
2. El middleware estaba validando permisos con JWT de acceso directamente contra RPC (`mi_contexto_permisos`), y ante fallo redirigía a `/unauthorized`.
3. El refresh de sesión existe en `/api/session`, pero no era la fuente central para el backend/server-side.

## Cambios implementados hoy

### 1) Middleware simplificado (sin autorización de negocio)

Archivo:
- `/var/www/talia/frontend/panel/middleware.ts`

Cambios:
- Se removió la validación de permisos por RPC desde middleware.
- Middleware queda como control de acceso básico por presencia de sesión en rutas clave.

Motivo:
- Evitar expulsiones por expiración del `access_token` durante navegación, antes de permitir renovación de sesión.

### 2) Nuevo SessionManager server-side

Archivo nuevo:
- `/var/www/talia/frontend/panel/src/lib/auth/server-session.ts`

Capacidades:
- Lee cookies de sesión.
- Evalúa vigencia del JWT (`exp`) con margen configurable (`minTtlSeconds`).
- Refresca tokens con Supabase (`grant_type=refresh_token`) cuando el token está vencido o próximo a vencer.
- Reescribe cookies de sesión cuando el contexto permite mutación.
- Expone funciones reutilizables:
  - `resolveServerSessionTokens(...)`
  - `resolveServerAccessToken(...)`

### 3) Integración del SessionManager en capas server-side

Archivos:
- `/var/www/talia/frontend/panel/src/lib/auth/panel-token.ts`
- `/var/www/talia/frontend/panel/src/lib/api/crm.ts`
- `/var/www/talia/frontend/panel/src/lib/supabase/rest.ts`

Cambios:
- Resolución de token ahora intenta usar acceso válido con refresh automático server-side.
- Fallback a service role se mantiene cuando no hay sesión de usuario válida.

### 4) Migración de endpoints API con token directo de cookie

Se migraron rutas que antes leían `ACCESS_TOKEN_COOKIE` de forma directa para usar resolución central con refresh automático (`resolveServerAccessToken`):
