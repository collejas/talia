# Incidente Postmark: lote de 1001 con persistencia parcial — 2026-10-02

## Estado

Incidente documentado. La entrega de los 1001 mensajes no está confirmada. No
se debe repetir el envío hasta terminar la conciliación por lote y destinatario.

## Evidencia

Tenant: `00000000-0000-0000-0000-000000000001`.

La petición del panel fue:

```text
POST /api/prospeccion/prospectos/contactar
HTTP 502
Duración aproximada: 42 segundos
```

La operación usó una clave de idempotencia HTTP, pero la columna
`solicitud_idempotencia` quedó nula en los lotes creados. Se observaron:

| Batch ID | Solicitados | Targets | Estado observado |
|---|---:|---:|---|
| `f126d4ea-cae3-4bd9-a501-a97b0ae61fad` | 1001 | 500 | 500 pendientes |
| `4e9070a1-8277-4603-b4b0-5092920b0771` | 1001 | 1001 | 500 fallidos, 500 procesando, 1 preparado |

El segundo lote registró un error de red al invocar
`worker_insert_postmark_contact_envios_bulk` y terminó con
`postmark_target_preparation_failed`.

Estos estados son internos de Talia. No equivalen a `MessageID`, aceptación,
entrega ni apertura en Postmark.

## Diagnóstico

### La API no es completamente asíncrona

La arquitectura documentada indica que la API debe crear el lote y encolar la
preparación. Sin embargo, el flujo actual todavía inserta targets y arranca
preparación durante la solicitud HTTP. La división en bloques de 500 reduce el
tamaño de cada llamada, pero no elimina el trabajo de la petición.

### La idempotencia aprobada no está operativa

La clave recibida del navegador no quedó persistida en
`prospeccion_contacto_batch`. Esto permite que un reintento cree un segundo
lote parcial.

La idempotencia debe existir en tres niveles:

1. Campaña: `organizacion_id + solicitud_idempotencia`.
2. Target: `batch_id + prospecto_id + canal`.
3. Evento externo: `MessageID + tipo_evento` y el identificador estable del
   webhook.

### El worker sufrió indisponibilidad de Supabase

Durante la preparación y la recepción de webhooks aparecieron errores de
timeout, red y schema cache. Un bloque pudo quedar fallido mientras otro
permanecía procesando. El worker debe reanudar bloques individuales sin
recrear los que ya tienen resultado durable.

## Plan de corrección

### 1. Conciliación antes de cualquier reenvío

- Obtener el estado de cada target de ambos lotes.
- Relacionar cada envío operativo con su `MessageID`.
- Consultar Postmark por `MessageID`; usar el destinatario solo como apoyo.
- Reconciliar webhooks pendientes y eventos históricos disponibles.
- Separar `no creado`, `creado pendiente`, `aceptado`, `entregado`, `rebotado`
  y `desconocido`.

### 2. Idempotencia y restricciones

- Persistir la clave durante la creación del batch.
- Agregar una restricción única por tenant y clave.
- Hacer que el endpoint devuelva el batch existente si la solicitud se repite.
- Mantener la restricción de target por `batch_id + prospecto_id + canal`.
- Registrar intentos y errores sin guardar secretos.

### 3. Preparación asíncrona real

- La API crea el batch y la orden de preparación; responde `202`.
- El preparador reclama bloques de máximo 500 con lease y `SKIP LOCKED`.
- Cada bloque tiene estado propio: `pendiente`, `procesando`, `preparado`,
  `fallido`, `listo_para_envio` y `enviado_al_proveedor`.
- Un reintento sólo procesa targets sin resultado durable.
- Un error de un bloque no cambia artificialmente el estado de los demás.

### 4. Envío a Postmark

- Cada bloque de hasta 500 forma un payload completo.
- El worker llama `/email/batch` una vez por bloque.
- La respuesta individual de Postmark se persiste por destinatario.
- No se usa una separación de cinco segundos entre mensajes individuales.
- Broadcast y transaccional permanecen separados.

### 5. Webhooks resistentes

- El endpoint persiste rápidamente la recepción idempotente.
- El procesamiento posterior se ejecuta en worker.
- Un fallo temporal de Supabase provoca reintento de la recepción, no pérdida
  del evento.
- Se monitorean respuestas 5xx, cola de webhooks, edad del evento más antiguo
  y tasa de reintentos.

## Criterios de aceptación

- Enviar 1001 crea una sola campaña y tres bloques: 500, 500 y 1.
- Repetir la misma petición no crea una segunda campaña.
- La API responde rápidamente sin esperar a Postmark.
- Cada bloque tiene resultados individuales verificables.
- Un timeout de Supabase permite reanudar sin duplicar.
- Talia no marca enviado un prospecto cuyo mensaje no fue creado o aceptado.
- Los eventos de Postmark quedan persistidos por tenant.

## Implementación ejecutada — 2026-10-02

Se cerró la primera fase del plan sin modificar el contrato de Brevo:

1. La API conserva la validación, selección y snapshot de la campaña, pero para
   Postmark encola un manifiesto durable en
   `prospeccion_postmark_campaign_preparation_jobs`.
2. La petición deja de insertar directamente los 1001 targets. Esto elimina el
   punto que produjo el `502` después de persistencia parcial.
3. `talia-postmark-preparer.service` reclama el trabajo, materializa los
   targets en llamadas acotadas y reanuda inserciones duplicadas sin crear
   envíos repetidos.
4. La preparación continúa separada del envío: solo después de preparar todos
   los destinatarios el flujo existente construye bloques Postmark de hasta
   500 y llama `/email/batch`.
5. Si Supabase falla, el trabajo queda pendiente/procesando con intento y
   error, en lugar de quedar oculto como un lote aceptado completo.

La tabla nueva usa `manifest` únicamente para contenido variable/renderizado;
tenant, lote, total, estado, intentos, lease y timestamps son columnas
explícitas. Sus RPC tienen `SECURITY DEFINER`, `search_path` fijo y permisos
solo para `service_role`.

### Verificación realizada

- Cola y RPC verificadas en Supabase.
- La cola estaba vacía después de la migración; no se alteraron lotes

- Pruebas de la ruta de contacto: `2 passed`.
