# Revisión de CRM y plan de migración multi-tenant

Este documento resume el estado actual del esquema (backup `backups/postgres_20251122_164957`), la configuración del backend y del panel React respecto al plan multi-tenant descrito en `docs/erd_crm_plan.md`. Incluye brechas y acciones recomendadas para aterrizar la migración.

## Hallazgos en la base de datos (backup)
- Las tablas clave (`clientes`, `contactos`, `usuarios`, `roles`, `usuarios_roles`) no incluyen `organizacion_id` ni políticas de RLS, por lo que cualquier adopción multi-tenant debe comenzar por introducir esa columna y aislar el acceso por tenant. 【F:backups/postgres_20251122_164957/postgres_20251122_164957_schema.sql†L1225-L1247】【F:backups/postgres_20251122_164957/postgres_20251122_164957_schema.sql†L10735-L10751】【F:backups/postgres_20251122_164957/postgres_20251122_164957_schema.sql†L10793-L10802】【F:backups/postgres_20251122_164957/postgres_20251122_164957_schema.sql†L11847-L11891】
- El pipeline actual depende de tableros y etapas de leads (`lead_tableros`, `lead_etapas`, `lead_tarjetas`, `lead_movimientos`), sin entidades de `cuentas`/`oportunidades`; la migración debe mapear estos tableros al nuevo pipeline de oportunidades. 【F:backups/postgres_20251122_164957/postgres_20251122_164957_schema.sql†L11264-L11298】【F:backups/postgres_20251122_164957/postgres_20251122_164957_schema.sql†L11325-L11336】
- Las actividades están partidas entre `conversaciones` y `llamadas` en vez de un modelo polimórfico con SLA, por lo que se requerirá consolidación en la tabla `actividades` propuesta. 【F:backups/postgres_20251122_164957/postgres_20251122_164957_schema.sql†L10758-L10775】【F:backups/postgres_20251122_164957/postgres_20251122_164957_schema.sql†L11379-L11392】

## Configuración del backend
- El backend usa variables de Supabase (`supabase_url`, `supabase_service_role`, `supabase_anon`) como fuente principal de datos, sin parámetros de tenant; cualquier separación por organización deberá añadirse a la configuración y propagarse a las llamadas. 【F:backend/app/core/config.py†L68-L119】
- Los endpoints del panel consumen directamente tablas actuales de Supabase (por ejemplo, `lead_tarjetas` y `lead_cotizaciones`), por lo que la migración del esquema exigirá adaptar estas consultas al nuevo modelo de `cuentas`/`oportunidades` y a RLS por `organizacion_id`. 【F:backend/app/api/routes/panel.py†L1589-L1624】

## Configuración del frontend (panel React)
- El panel obtiene la URL del backend a través de variables de entorno (`PANEL_API_URL`, `NEXT_PUBLIC_PANEL_API_URL`, etc.), por lo que será necesario alinear estos valores cuando cambien los endpoints polimórficos propuestos. 【F:frontend/panel/src/lib/api/panel.ts†L1-L18】
- La inicialización de Supabase en el frontend depende únicamente de `SUPABASE_URL`/`SUPABASE_ANON_KEY`, sin noción de tenant; deberá incorporar el contexto de `organizacion_id` que se introduzca en el backend. 【F:frontend/panel/src/lib/auth/supabase.ts†L1-L15】
- Las acciones del embudo trabajan con el esquema actual (`lead_tarjetas`, RPC `panel_lead_update`), por lo que deberán reescribirse para operar sobre `oportunidades`, `cuentas` y el historial de etapas propuesto. 【F:frontend/panel/src/lib/embudo/actions.ts†L471-L507】

## Acciones recomendadas alineadas al plan
- Seguir los pasos 1-4 del plan para crear tablas base con `organizacion_id`, núcleo de CRM (`cuentas`, `contactos`, `oportunidades`) y la tabla unificada de `actividades` con SLA, migrando los datos existentes desde `lead_*`, `conversaciones` y `llamadas`. 【F:docs/erd_crm_plan.md†L100-L110】【F:docs/erd_crm_plan.md†L123-L133】
- Ajustar el backend: añadir `organizacion_id` y `propietario_usuario_id` a los payloads, refactorizar las llamadas Supabase hacia las nuevas tablas/funciones y aplicar RLS. 【F:docs/erd_crm_plan.md†L100-L110】
- Ajustar el frontend: parametrizar `organizacion_id` en las llamadas, actualizar componentes del embudo y formularios para prioridad/fecha de vencimiento de actividades, y preparar UI reutilizable para archivos, tags y notas polimórficas. 【F:docs/erd_crm_plan.md†L123-L133】

- Se incorporó la tabla unificada de `actividades`/tareas con prioridad, `fecha_vencimiento`, `sla_horas`, `recordatorio_en` y RLS por `organizacion_id`, cubriendo el paso 4 del plan para SLA y recordatorios. 【F:supabase/migrations/20260617_000002_actividades.sql†L1-L67】
- Se agregaron tablas para soporte (`tickets`, `ticket_comentarios`), ventas avanzadas (`productos`, `cotizaciones`, `cotizacion_items`), marketing (`campanas`, `leads`, `lead_eventos`) y elementos transversales (`tags`, `taggings`, `archivos`, `notas`, `audit_logs`) todas con índices y RLS por `organizacion_id`, alineando los pasos 5-9 del plan multi-tenant. 【F:supabase/migrations/20260618_000003_support_sales_marketing.sql†L1-L243】
- Se añadió una migración puente para tablas legadas (`clientes`, `contactos`, `usuarios`, `roles`, tableros/etapas/tarjetas/historial de leads, `conversaciones`, `llamadas`) que agrega `organizacion_id`, crea un tenant por defecto si es necesario y aplica RLS basada en `current_organizacion_id()` para mantener compatibilidad durante la transición. 【F:supabase/migrations/20260619_000004_legacy_multitenant_bridge.sql†L1-L94】

## Qué falta para cerrar el plan
- **Migrar datos existentes al nuevo modelo**: mapear los tableros y tarjetas de `lead_*` hacia `oportunidades`/`etapas_pipeline` y consolidar `conversaciones`/`llamadas` en `actividades`, preservando historial y propietarios antes de encender RLS en producción.
- **Conectar el frontend**: mover las vistas del embudo y formularios actuales a los endpoints `/crm`, exponiendo prioridad y fecha de vencimiento en actividades y respetando `organizacion_id`/propietario en los payloads.
- **Refactorizar integraciones de archivos/etiquetas/notas**: reemplazar llamadas directas a tablas antiguas por los endpoints polimórficos `/crm/archivos`, `/crm/taggings` y `/crm/notas`, validando `relacion_tipo` permitido.
- **Validar RLS y autenticación**: probar con tokens de tenants distintos que las políticas `current_organizacion_id()` aíslan los registros y que el `service_role` conserva acceso administrativo para migraciones y jobs.
- **Automatizar verificaciones**: añadir suites de pruebas para los nuevos endpoints `/crm` (por ejemplo con `httpx.AsyncClient`) y ajustar `make check-all`/CI para ejecutar lint + pruebas backend/frontend tras la refactorización.
